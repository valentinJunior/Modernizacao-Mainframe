# Technical decisions — servico-juros

[🇧🇷 Português](DECISOES.md) | 🇺🇸 English

Log of the decisions made while converting JURB0100/JURS0100. Each one references the section of `spec-microservico-java.en.md` that motivated it.

## D1 — `BigDecimal` with the COBOL scales (spec §4)

| Item | COBOL | Java |
| --- | --- | --- |
| Monetary values | `S9(13)V99 COMP-3` | scale 2, `HALF_UP` |
| Rates | `S9(3)V9(4) COMP-3` | scale 4 |
| Exponent days/30 | `S9(3)V9(9)` `ROUNDED` | scale 9, `HALF_UP` |
| Interest factor | `S9(3)V9(12)` `ROUNDED` | scale 12, `HALF_UP` |

The intermediate calculations for late-payment interest and late fee use `MathContext.DECIMAL128` (34 digits), in the same operand order as the `COMPUTE`, and round only at the end.

## D2 — Fractional power in `double`, in a single place (spec §4)

`(1 + taxa/100) ^ (dias/30)` has no exact `BigDecimal` solution for a fractional exponent. Enterprise COBOL also resolves this `**` in floating point. The computation is isolated in `PotenciaFracionaria.calcularFatorJuros`: `Math.pow`, exact conversion with `new BigDecimal(double)` and immediate rounding to scale 12.

It is the only production file that uses `double`, and the `DinheiroSemDoubleTest` test enforces this. If a one-cent difference shows up against real mainframe data, the investigation starts here.

## D3 — Balance and dates received as text (spec §6)

`saldoDevedor` and the three dates arrive as `String` in the JSON. The reasons:

- validation is done by the domain, with the same codes and the same order as the COBOL (21, 30, 31, 33);
- in a batch request, a malformed date in one contract becomes a rejection of that contract, instead of bringing down the whole request with a deserialization error.

The balance is also accepted as a JSON number (`100000.00`) and follows the semantics of a `MOVE` to `S9(13)V99`: it truncates beyond the 2nd decimal place and beyond the 13th integer digit, silently (DIVERGENCIAS V1). Dates follow strict `AAAA-MM-DD` (YYYY-MM-DD), with calendar validation: `2026-02-30` is invalid, as in `TEST-DATE-YYYYMMDD`.

## D4 — Request structure errors: `ENTRADA_INVALIDA` (spec §6)

The legacy has no code for "missing contract number" or "malformed JSON", because such things do not exist in a fixed-layout file. These cases return HTTP 400 with `codigo = "ENTRADA_INVALIDA"`, so they are not mixed up with business codes 01 to 40.

## D5 — Order of validations (spec §6)

Inside the domain, the order is the COBOL's: 21, 20, 10, 30, 31, 33, 32 and 40. In the application layer, before the domain, come:

1. **33 (invalid reference date):** without a valid date there is no way to know which rate is in effect. In the legacy, the date comes in the PARM and JURB0100 aborts the whole job if it is wrong.
2. **01 (product without a rate):** in the legacy this is also checked before the `CALL JURS0100`.

## D6 — HTTP status per code

We follow the spec's table: 422 for business rules (01, 10, 20, 32, 40) and 400 for malformed data (21, 30, 31, 33). In the `GET /v1/taxas/{produto}` lookup, a product without a rate returns **404** with code 01, because there it is a resource lookup, not a calculation.

## D7 — Rating: `trim`, no uppercase conversion

The COBOL compares `'B '` with `'B '`. We strip the padding spaces, but we do **not** convert lowercase: `"b"` is rejected with 40, as it would be in the legacy.

## D8 — Spread and rates with validity periods, looked up by reference date (spec §5)

- `TB_SPREAD_RATING` is loaded with the exact values from the JURS0100 `EVALUATE`. The start dates follow the source's change history: 2019-05-08 for AA to E and 2021-02-11 for F, G and H.
- In a batch request, the spread table is read once per reference date.
- Rates are looked up by product and date, with no 500-product limit.
- If there is more than one rate in effect for the same product and date, the service fails with an internal error, as the legacy does by aborting with RC 16.

## D9 — Build and tests in a container

The workstation has only JRE 25, without `javac`. The build runs in the `eclipse-temurin:25-jdk` container, with Podman, and Maven comes via `mvnw`. The multi-stage Dockerfile runs the tests during the image build: no image is produced without validated equivalence.

## D10 — Origin of the equivalence dataset

`src/test/resources/equivalencia/casos.csv` has 27 cases:

- 2 come directly from the Technical Documentation JURD0100 (R$ 4,383.33 and R$ 67.67);
- the other 25 (edge cases, half-cent ties and rejections) were generated by `ferramentas/referencia_jurs0100.py`, a reference implementation in Python, independent of the Java code, written from the COBOL semantics.

**Validation against the real COBOL (2026-11-25).** The 27 cases were run on the original `JURS0100`, compiled with GnuCOBOL 3.2 in `-std=ibm` mode (folder `equivalencia-cobol/` at the project root). All 27 matched `casos.csv` in every field, so the dataset no longer depends solely on the reference implementation.

**This still does not replace real production data**, because GnuCOBOL is not the production compiler. The next step is to extract JUROSOUT from a run of JURD0100 on the mainframe, convert it from EBCDIC/COMP-3 to CSV and append the rows to the same file.

## D11 — Half-cent tie cases

A mutation test (replacing `HALF_UP` with `HALF_EVEN` in the calculator) showed that the first version of the dataset did not detect the change: no case landed exactly on a half cent. `empate_meio_centavo_multa` (late fee of 2.005 → 2.01) and `empate_meio_centavo_mora` (late-payment interest of 0.005 → 0.01) were added. With them, the same mutation fails 2 cases.

When the real mainframe data arrives, it is worth repeating this mutation test to confirm that it also covers the ties.

## D12 — Balance format validated before `BigDecimal` (finding from an external review)

**Problem.** The balance arrives as text (D3) and was converted directly with `new BigDecimal(texto)`, which accepts scientific notation. An external review found the following, and it was reproduced on the published image:

| Balance sent | Before the fix |
| --- | --- |
| `"1E+50000000"` | 44 s of CPU on a single request, ending with code 20, a wrong message. With the 1,000-contract batch, one request can lock up the service (denial of service) |
| `"1E+999999999"` | Unhandled `ArithmeticException` and HTTP 500 |
| `"1E+3"` | Accepted as 1,000.00, a format the COBOL never receives |

**Decision.** Before conversion, the text must match `-?\d{1,18}(\.\d{1,9})?` and be at most 40 characters long. Otherwise, the balance is "non-numeric content", code 21, the same code the COBOL returns for invalid data in the field. The cost of the conversion is bounded, whatever the input.

**Tests.** 15 new cases, with a time limit, cover scientific notation, hexadecimal, `NaN`, `Infinity`, a 5-million-digit string, the batch endpoint and the V1 rule. With the old code, all 15 fail.

**Lesson recorded.** The first version was generated by an AI agent and passed the 53 original tests, because none of them exercised hostile input. The flaw was caught by human review. Equivalence tests prove that the calculation is correct, but they do not replace a security review of the boundary.
